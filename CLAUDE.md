# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## The token-economy doctrine — STANDING DIRECTIVE: the cheapest channel that proves it

**Permanent instruction from the project owner: every question goes through the cheapest channel that can prove its answer.** Two measured costs drive it. A graph lookup answers a question for **~2.3k tokens instead of reading a 2 000-line HTML file** (measured: 10.5× fewer tokens per question). And **every turn re-sends the whole accumulated context** — a file read at turn 5 is paid again at turns 6, 7, 8…, quadratic in session length — while a subagent has its own window and returns **only its conclusion**. The graph fights the cost of *one* lookup; delegation fights the cost of the *session*, the bigger bill.

**The ladder — take the lowest rung that actually proves the answer:**

1. **The graph first** (`graphify explain/query/path`, ~2.3k tokens) for any question of structure, code or flow it covers. The repo carries a knowledge graph of itself in `graphify-out/` (every function of `app.html`, the notebook's sections and markup contract, the design rules, the traps — counts and provenance in docs/ARCHITECTURE.md § graphe). Before opening `app.html`, `vocabulaire_hebreu.html` or `flashcards_hebreu.html` to find something:

   ```bash
   graphify explain "checkAnswer"     # exact source line + every caller/callee, ~15 lines
   graphify query "comment la révision espacée écrit-elle dans localStorage ?"
   graphify path "deriveCartes" "recordResult"    # how two things connect
   ```

   `graphify explain` is why this file carries no `near line NNN` pointers: **line anchors drift** in this repo; the graph re-derives them mechanically. It is a snapshot: **a graph/file disagreement is settled for the file**.

   ⚠️ **Know how stale it is before you trust it.** The graph predates the repository's reorganisation into `data/`, `src/` and `tools/`, so it does **not** know `data/`, `src/carnet/`, `src/app/`, `src/portail/`, `tools/`, `docs/` or `.githooks/` — and its `app.html` functions are mapped at lines from before the JS was reordered into 14 modules. It also carries a **dead community on a file that no longer exists** (`audit_carnet_mecanique.js`, since deleted). For anything under `src/`, `tools/` or `docs/`, go straight to rung 2 (`grep -n` on the module named by the `// Expose :` headers, listed in docs/ARCHITECTURE.md § Anatomie de l'app). The graph stays reliable on what has not moved: the notebook's structure, the design rules, the traps. Pending debt is flagged in docs/TODO.md § « Dette de graphe » (`grep -c '^- \*\*' docs/TODO.md` for the count), and **no flag triggers anything**. Rebuilding is **never automatic** — `/graphify . --update` costs **~235k tokens** and runs only on an explicit decision (ritual step 5 carries the flag rule; refresh-cost history in docs/ARCHITECTURE.md § graphe). `graphify-out/GRAPH_REPORT.md` holds the audit trail (god nodes, bridges, EXTRACTED/INFERRED/AMBIGUOUS provenance).

2. **A short grep** (≤ ~15 lines of output) for a point fact the graph doesn't carry — cheaper than an agent round-trip.

3. **A subagent** as soon as the answer requires volume. **The test is the ratio, not the difficulty: much intermediate output, short verdict → delegate.** Mandatory in this repo: **every WebKit/Playwright run** (dozens of driving round-trips and screenshots — among the most expensive things a context can hold — for a three-line verdict; the single biggest win); **`node tools/build.js` / `verifie_exemples.js` on a batch** (you want the counts and the named errors, not the log); **broad exploration and any bulk file reading** the graph can't answer in one query; **material audits and content drafting on batches** (vocabulary lots, counter-expertise, dry-run validation) — only verdicts and arbitrages surface.

4. **The main thread keeps only**: charter/design judgment (docs/DESIGN.md's named rules), content arbitration, the edits themselves, commits, and the documentation pass. These need the accumulated context and the project's voice — exactly what a subagent doesn't have. Read a file in full only when you are about to **edit** it, or when the graph's answer is genuinely insufficient.

**The coupling between rungs 1 and 3 — explicit, both directions:**

- **Subagents inherit this file, so rung 1 binds them too**: an agent must ask the graph before opening a file. And because an agent gets this file but not your conversation, **every scouting prompt must repeat it** — « demande au graphe avant d'ouvrir un fichier » — alongside the numbered criteria.
- **The reverse routing rule: what the graph already knows never goes to a subagent.** A ~2.3k-token `explain` beats a ~30k-token agent; dispatching an agent to rediscover graph content pays rung-3 prices for a rung-1 question.

**How to run the agents**:

1. **Parallel fan-out when independent** — launch all independent agents in ONE message. A 12-check campaign is 3 agents by theme, not 1 giant or 12 tiny ones.
2. **Numbered criteria in every prompt**: "count X, name every failure, PASS/FAIL per item, max N lines, no screenshots/HTML in the reply" — state the acceptance bar *in the prompt*. An agent that answers « c'est bon » proved nothing: a muted control always passes green (same lesson as the coverage guard in `tools/build.js`).
3. **Reuse a finished agent for follow-ups in its area** (continue it with a new message) instead of spawning a fresh one — its context is already paid for.
4. **Never read an agent's transcript/output file, a screenshot, or a raw log in the main thread.** If the report is insufficient, send the agent a follow-up question.
5. **Model per task (owner's rule)**: dispatch mechanical scouting on **Sonnet 5** (`model: 'sonnet'`) — bulk grep, `tools/build.js`/`tools/verifie_exemples.js` counts, broad/large-file reading, WebKit driving for a short verdict: cheaper, amply sufficient. **Opus 4.8 (the default, inherited) is reserved for content arbitration and charter (docs/DESIGN.md) judgment** — exactly the work rung 4 keeps on the main thread anyway, so a subagent almost never needs it. When unsure, the task is mechanical → Sonnet.

**One session per chantier**, then `/clear`. The ritual's closing commit is the clean cut point: the state lives in git and in docs/TODO.md « Reprendre ici », not in the context window.

## What this is

A French-language toolkit for learning modern Hebrew, deployed as static files on GitHub Pages at `https://rubischthagadol.github.io/flashcards-hebreu/`. There are **no dependencies, no tests, no package manager** — every deployed file is a single self-contained HTML document with inline CSS and vanilla JS. The only tooling is `tools/build.js`, `tools/verifie_exemples.js`, `tools/ajoute_mots.js`, `tools/cherche_mots.js`, `tools/mesure_translitteration.js`, `tools/controle_tr.js` and `tools/propose_ktiv_male.js` (dev-only, zero-dependency Node scripts, not deployed; all seven live in `tools/`; `build.js` computes the repo root as `path.join(__dirname, '..')` and exports it as `ROOT`, so no other tool ever recomputes it — `controle_tr.js` needs no root at all, it takes its file from `process.argv[2]`; `ajoute_mots.js` is the stage-1 word-sheet generator, contract in docs/SPEC_AJOUTE_MOTS.md — it inserts new entries into `data/*.json` from a small JSON, validates in a sandbox, and only writes with `--ecrire`; `cherche_mots.js` is the read-only consultation channel of trap 15 — `node tools/cherche_mots.js TERME…` answers "does this word exist? where?" and `--stats` shows theme/level gaps, for ~200 tokens instead of reading the notebook; `mesure_translitteration.js` scores `he2tr` against every hand-written `.tr` — the harness that must be re-run before touching the initial-shva rule, see § Transliteration standard; `controle_tr.js` checks a word sheet's hand-written `tr` against `he2tr`, entry by entry — heads, examples and forms alike — distinguishing `✔ replié` (a display-only divergence `trKey` folds away) from `✘ BRUT` (a real disagreement), exit 1 on any brut; every word sheet runs through it before insertion). To develop, open the files in a browser; to deploy, replace files on the `main` branch (GitHub Pages redeploys automatically, same URLs).

The five deployed pieces: **`vocabulaire_hebreu.html`** (the notebook — generated by `node tools/build.js` from `data/*.json` + `src/carnet/`; never edit it directly), **`index.html`** (the portal / root page — **generated**: `assemblePortail()` injects `src/tokens.css` into `src/portail/index.html`; **edit the portal in `src/portail/`, never in `index.html`**), **`app.html`** (the online flashcards, fetches `cards.json` at load — **generated too**: `assembleApp()` builds it from `src/app/coquille.html` + `src/tokens.css` + the 6 CSS fragments and 14 JS modules of `src/app/`, ordered by `src/app/ordre.json`; **edit the app in `src/app/`, never in `app.html`**), **`flashcards_hebreu.html`** (the standalone offline build, cards inlined by the same build), and the PWA layer (`manifest.webmanifest`, `sw.js`, `icons/`). `data/*.json` is the single source of truth for all content. Ask the graph for what any of them contains; docs/ARCHITECTURE.md holds the prose version.

Important: `app.html` uses `fetch()`, so it must be served over HTTP, not opened as a `file://`. Run a local server from the repo root (`python3 -m http.server`) and open `http://localhost:8000/`.

## ⚠️ The traps — these do not live in the graph, because they must fire before you ask

Each of these was paid for once. They are listed inline because a graph query only helps an agent who already suspects there is something to know.

1. **No deployed HTML at the repo root is hand-edited any more — not one.** `flashcards_hebreu.html`, `vocabulaire_hebreu.html`, `cards.json`, `app.html` and `index.html` are 100% generated by `node tools/build.js` from `data/*.json` + `src/carnet/` + `src/app/` + `src/portail/` (the standalone is derived from the app assembled in memory, never from the `app.html` on disk). Hand edits are erased on the next build; `node tools/build.js --check` compares all five.
2. **Never use `transition:all` in the app's CSS (`src/app/css/`).** The shorthand captures the `outline-*` longhands; WebKit then pins them to their initial values, so a focused element renders WebKit's UA ring instead of the gold one *while still matching `:focus-visible`*. This silently cost the 40+ chips and the cards-mode buttons their focus ring. Always list the animated properties explicitly (`background, color, border-color, opacity`). Mechanized: `verifieCharte()` fails the build on any `transition:…all` in the assembled app — and in the generated portal too (it has its own gold focus ring and animates its doors, so it runs the identical risk; `src/portail/index.html`).
3. **`font-size:22px` sits on `body`, never on `html`, in all three files — so `1rem` is 16px, not 22px** (measured in WebKit). Do not "fix" this by moving the 22px to `html`: it would scale every `rem` by 1.375 here *and* in `app.html`, whose sizes are tuned to what they actually render.
4. **The notebook holds three `:root` blocks, and they never merge.** (1) the shared design tokens — see trap 5; (2) the 8-step type ramp (`--pas-titre` 2.3rem … `--pas-micro` 0.7rem): **no literal `font-size` may remain outside it**, the single named exception being `1.15em` on Hebrew embedded in French prose; (3) the reading column (`--colonne` 28rem, `--colonne-large` 56rem). Both local blocks are **measured values, not preferences**: `--colonne-large` is a floor (raising it is a trap) and `--colonne` is calibrated on the prose's real advance, never a digit's width. docs/DESIGN.md §3 carries the measurements and the three traps paid for them.
5. **The first `:root` design-token block is byte-identical between the notebook, the app and the portal — by construction, no longer by discipline.** Its single source is `src/tokens.css`, injected at build time into all three at their `<!-- @TOKENS -->` marker (raw for the notebook, re-indented 2 spaces for the app and the portal). There is no hand-maintained copy left anywhere. What `verifieCharte()` still enforces, because injection alone can't: each deployed page carries the tokens *verbatim* and opens the **expected number** of `:root` blocks (notebook 3 — cf. trap 4 —, app 1, portal 1), so a second hard-coded `:root` can't win by cascade; and `manifest.webmanifest`/`theme-color` track `--bg`. If `--bg`/`--gold` change, regenerate the icons too — no command checks that.
6. **Every Hebrew node carries `lang="he"`** — emitted by `src/carnet/gabarits.js` for every node of the generated notebook (100%; count measured in a browser) and by the app's render modules (`src/app/js/`, chiefly `10-rendu.js`) for every generated node (`.big-he`, `.sub-he`, `.cursive-line`, `.f-he`, `.qc-he`, `.sr-he`, `.srd-he`, `.m-he`, feedback `.he`, brand `.he`). Keep it when touching `gabarits.js` or those template strings. ⚠️ The notebook count must be **measured in a browser, not computed from the source**: a new entry also creates its generated `span.cursive`, so one word is worth more than one node.
7. **Gold never appears on an inactive state** (docs/DESIGN.md, règle de la lampe), and no surface is gold-tinted at rest — the app's « Révision du jour » card is the single licensed exception. `border:1px dashed` means **only** "nothing here" (`.empty`); warning boxes use `.attention`, solid rule.
8. **`niveau` is mandatory in `data/*.json`** on every entry — tables (`data/noms.json`, `data/adjectifs.json`, `data/verbes.json`) and lists (`data/listes/*.json`) alike. `valideDonnees()` in `tools/build.js` fails naming the offending word if any entry comes out without a `niveau` in `EXPECTED_LEVELS`. The generated notebook only carries the result, and the app's tolerance for unclassified cards is a safety net, not a licence. **`theme` follows the same regime but only on the three table files** (slug must be in `EXPECTED_THEMES`, its list aligned with `THEMES` in `src/app/js/07-filtres.js`, a guard the build enforces; a `theme` on a list entry is an error — lists are mono-theme by nature). Every future entry must carry both fields; the build enforces it.
9. **Every entry of the Noms/Adjectifs/Verbes tables must carry at least one example** (verbs: a present-tense sentence). `verifie_exemples.js` treats a missing `<ul class="exemples">` as a blocking error.
10. **Never bump `VERSION` in `sw.js` by hand.** The line is **stamped by `node tools/build.js`** with a sha256 of the five artefacts + `manifest.webmanifest`, and `--check` recalculates it (named FAIL on a mismatch), so an artefact can no longer be committed without its stamp. Editing the value by hand is pointless: the build rewrites it and `--check` rejects it. Two assumed corollaries, both stated in `sw.js`'s own header: **`sw.js` is never in its own hash** (the version is written there — including it would make the hash chase its own tail, and `--check` could never go green), and **`icons/` is not in it either** — a changed icon doesn't move the version, which costs one launch of staleness since everything same-origin is stale-while-revalidate. To force a real cache purge (a strategy change that makes kept entries harmful), hand-edit the `CACHE` prefix in `sw.js` — the only manual gesture left on that file.
11. **The service worker registration lives inside the `BUILD:ONLINE-ONLY` fence** of `src/app/js/99-principal.js` and must stay there — `generateStandalone()` strips the whole fence, and `serviceWorker` is a forbidden token in the standalone (the build fails if one leaks out). The fence must stay a **single** block: split in two, the strip only removes the first half. The portal has its own snippet.
12. **WSL tooling**: visual checks run through **Playwright + real WebKit** (`devices['iPhone 16 Pro']`), pure logic through jsdom. The system headless Chrome **hangs in WSL2 — never use it**. Details in docs/RITUEL.md § Outillage.
13. ⚠️ **Our visual checks are iPhone-emulated, so a desktop-only defect is invisible to them.** (An over-wide reading column once survived every critique because the phone viewport bounded the text on its own.) **When you touch layout, measure at desktop widths too** (1440/1280/992/900/768), not only on the phone. Those widths are not arbitrary samples: **the app's desktop tier starts at `min-width:900px`** (`src/app/css/30-cartes.css` and `40-reponses.css`, documented in docs/DESIGN.md § Le palier « ordi » de l'app), so 900 and 992 straddle the boundary and 768 proves the phone side of it. Symmetrically, a layout change proven on desktop must be shown to leave the phone **identical** — that comparison is what catches a fix that quietly costs mobile something.
14. ⚠️ **An emulated timing is worthless in absolute terms — it is only ever valid compared to itself.** Emulation runs a desktop CPU through a phone-shaped viewport; it models layout, not performance (paid for once: emulated 329 ms on a first render the real iPhone did in 41 ms — the device was *faster* than the dev machine; detail in memory chantier-lag-iphone). **Use emulated timings only as A/B deltas** (before vs after). For any absolute claim about how the app *feels*, measure on the device — the « Diagnostic de latence » block in « Réglages avancés » is for that. Mirror of trap 13: there emulation hid a real desktop defect, here it invented an imaginary mobile one.
15. ⚠️ **A question of existence, count or location is NEVER paid for by reading a file or dispatching a subagent — a command answers it directly**: `node tools/cherche_mots.js` (notebook: words, French senses, line anchors, `--stats` for theme/level gaps), `graphify explain` (code), `grep -n` (the rest). Corollaries: (a) never `Read` a file over ~30 KB without `offset/limit` — the notebook, `app.html`, `flashcards_hebreu.html`, `docs/ARCHITECTURE.md`, `docs/DESIGN.md`, `docs/TODO_ARCHIVE.md` all qualify. Get the target line from a command first (`cherche_mots.js` for content, `graphify explain` for code, `grep -n` on a section title for `.md` docs), then read ±30 lines around it — this includes the ritual's documentation pass, which edits sections, never re-reads whole files; (b) never paste a list, log or inventory longer than ~20 lines into a reply — named verdicts and `file:line` references only; (c) the counter-example that earned this rule: a subagent inventory of the notebook cost **56k tokens** to learn that 24 words were absent — the same answer costs ~200 tokens by command.

16. ⚠️ **A horizontal overflow is NOT visible on `getBoundingClientRect()` of elements — measure text nodes with a `Range`.** Third of the same family as traps 13 and 14 (there emulation hid a desktop defect, then invented a mobile one; here the standard measurement simply doesn't see the defect at all). Under flex, boxes shrink as instructed (`flex-shrink:1`, `min-width:0`) and only the **text** paints past them, without enlarging its element's rect. A sweep over `document.querySelectorAll('*')` therefore reports **zero right-overflow** while `document.documentElement.scrollWidth` is 42px over `clientWidth`. Two consecutive investigations concluded wrongly before this was seen. Two corollaries, both paid for: a "not clipped by a scrollable ancestor" filter names a **plausible and false** culprit (it fingered a gloss that overflowed *left*, which cannot add to `scrollWidth` at all); and **left overflow never grows `scrollWidth`** — only the right edge does, so a fix that visibly reseats an element can leave the number untouched. And the usual cause in this repo is trap-adjacent: **`display:contents` removes the box, not the inheritance**, so `th,td{white-space:nowrap}` keeps descending into a dissolved cell (docs/DESIGN.md § Rangs en cartes).

17. ⚠️ **Our visual bench has overlay scrollbars; the owner's browser has classic ones — a 1px overflow is invisible on one and disfiguring on the other.** Fourth of the family of traps 13, 14 and 16. Playwright/WebKit on Linux paints nothing for 1px of overflow; Chrome/Edge on Windows paints a full arrowed scrollbar **and takes 15px of width away from the content**. Paid for once: `#face-content` sat at `clientHeight` 152 against `scrollHeight` 153 — engines round the same fraction to different sides — and **80 WebKit cells reported a margin of *exactly* zero, everywhere**, which read as "fits" when it meant "one rounding away from broken". Two hypotheses (a flex intrinsic-sizing divergence, then a font-fallback difference) were built and refuted before anyone looked at the right number. Three corollaries, all paid for: (a) **a margin measured at zero is not a margin** — treat it as a defect pending a rounding; (b) when a visual defect does not reproduce on the bench, **ask for the measurement on the real browser before theorising** — one line pasted into the console settled in ten seconds what two full campaigns could not; (c) ⚠️ **DevTools docked to the right shrinks `innerWidth`** and flips the page into another media-query tier, so the first measurement obtained that way described the phone tier, not the one in the screenshot — say « dock to bottom, or undock » when asking for console numbers.

18. ⚠️ **A global behaviour hidden inside one section file breaks everything downstream of it, silently.** The notebook's cursive lines and its `</main>` both lived in `src/carnet/sections/41-phrases.html` — and **two sections follow it in the registry**. So « Abréviations et sigles » and « Hébreu parlé » rendered *outside* `<main>` and lost the reading column (`main > *`), i.e. two whole sections unbounded on desktop. Nothing showed it: the notebook was complete, `--check` green, and the phone bench bounds width on its own (trap 13 again). Both now live where they belong — `src/carnet/pied.html`, always assembled last, and `src/carnet/cursive.js` — and `verifieStructureCarnet()` fails the build on a `<h2 id="sec-…">` after `</main>`. **Corollary for any guard that reads markup: strip `<script>` blocks first** — the injected JS is text, and a comment quoting `<main>` is not a tag (the guard failed on a correct notebook before this). Mirror of the `verifieCharte()` lesson, which only scans `<style>`.

19. ⚠️ **Ktiv male cannot be derived from the nikud — and unlike the shva, there is nothing to measure it against.** `data/` stores vocalised *ktiv haser* (`מְסֻבָּךְ`); both surfaces display nikud-free lines that merely *strip the points* (`מסבך`), a spelling no real text uses — the notebook's cursive line (~5573 of them) and the app's. `tools/propose_ktiv_male.js` proposes and counts: **1524 of 5376 forms differ** (383 headwords), of which 915 are mechanical (kubutz/holam/hirik) and 609 need arbitration. The proof that no rule closes it: `לַיְלָה` and `בַּיְשָׁן` carry the **identical** pattern (patach, yod, shva) and give `לילה` (one yod) against `ביישן` (two). And there is **no harness** — `he2tr` could be tuned against 4725 hand-written `.tr`, whereas `data/` holds no hand-written full spelling at all. So the tool PROPOSES, it never decides; the intended regime is the `.tr` one (hand-written wins). Do not "fix" this with a generator.

## The data pipeline (the one thing to understand before editing anything)

**Nothing in this repo reads HTML any more — the build only ever writes it.** The last extractor is gone, and so are the leftover helpers that outlived it. Consequence to hold onto: **no artefact is ever an input**, so a hand edit in one is not merely lost — it is invisible to every tool. That claim is literally true: `verifie_exemples.js` and `ajoute_mots.js` no longer grab `he2tr`/`trKey`/`editDist` out of `app.html` by text-slicing; they now call **`fonctionsApp(names, root)`** (exported by `build.js`), which evaluates the source module `src/app/js/02-translitteration.js` whole in a `vm` sandbox. Need one of those functions in a Node tool? Call `fonctionsApp` — never re-implement a transliteration, and never read an artefact to get one. `data/*.json` (`noms.json`, `adjectifs.json`, `verbes.json`, `listes/<slug>.json`; schema in `data/SCHEMA.md`) is the only content input; `src/carnet/` (`gabarits.js`, `carnet.css`, `carnet.js`, `pied.html`, `sections/`) holds the pure notebook templates. `node tools/build.js` runs `chargeDonnees()` → `valideDonnees()` → `genereCarnet()` (the notebook HTML), `deriveCartes()` → `assertFormeCartes()` (the card array, written to `cards.json`), then `assembleApp()` (`app.html`, from `src/app/`), `generateStandalone()` (the standalone, derived from that freshly assembled app with the cards inlined) and `assemblePortail()` (`index.html`, from `src/portail/`), then **stamps `VERSION` in `sw.js`** with a hash of what it just wrote (trap 10). **Edit content in `data/`, app code in `src/app/`, the portal in `src/portail/` — never in an artefact**: `vocabulaire_hebreu.html`, `cards.json`, `app.html`, `flashcards_hebreu.html` and `index.html` are all regenerated and any hand edit is lost.

What still matters when touching `data/`:

- A list file's `section` field is the routing key: it must match an entry in `listCats`/`EXPECTED_CATS` (`tools/build.js`), or the section is silently excluded from cards.
- `.tr`/`tr` values are **authoritative** — copied verbatim into cards, never regenerated from `he2tr`.
- `note` fields render **everywhere** — tables and lists alike (`.note-line` in the notebook via `vedette`/`itemListe`, card back in the app; `deriveCartes` copies them for all branches, Hebrew wrapped `lang="he"` via `escFr` at derivation). A note carries usage facts of the language only (rections, register, disambiguation) — never project narration, changelog or "already in the notebook" bookkeeping (owner's rule).
- The card schema is unchanged in shape (`{cat, he, tr, fr, note?, niveau?, theme?, exemples?:[{he, tr, fr, he_plain}], he_plain, forms?:[{he, tr, label, he_plain}], genre?}`) — its single source is now `deriveCartes(donnees)`. Table-derived cards have `tr:''`; the UI falls back to `he2tr(card.he)`. Full detail in docs/ARCHITECTURE.md §3.

## Transliteration standard

All notebook `.tr` values and `he2tr` output follow it: `kh` = khaf without dagesh, `ch` = het (final furtive patach → `ach`), `ts` = tsadi, `'` = ayin everywhere (`'ivrit`, `be'er`, `yode'a`) and alef between two vowels (`tsme'ah`), final hey kept (`atah`, `zeh`), `ei` for tsere/segol+yud (`beit`), `u`/`f`/`k`/`v` (never `ou`/`ph`/`q`/`w`). Initial cluster shva is written only when heard (`gdolim` but `ledaber`). **Kamats katan in the כל root is `o`, never `a`** (`kol`, `bekhol`, `lekhol`) — and *only* when that ל closes the word, or `כַּלְכָּלִי` comes out `kalkoli`. **Patach + mute yod + vav is `av`** (`akhshav`, `stav`), never `ayv`.

⚠️ **Three corollaries of that same standard, each caught only after tripping up a word sheet across ~285 entries.** The final hey stays even in feminine/ordinal endings, not just the obvious cases (`shloshah`, `harishonah` — never `shlosha`). The ayin `'` holds at **every** position, word-initial and word-final included, not only medial (`'eser`, `'asarah`, `reva'`). And the 2nd-person masculine suffix ־ךָ is a khaf, so `-kha` — never `-cha`.

⚠️ **The notebook is authoritative — don't blindly regenerate hand-written `.tr` values from `he2tr`.** Thanks to `trKey`'s folding the standard is display-only: typing stays tolerant to all variants. When changing acceptance behaviour, edit `trKey` and `he2tr` **together** — they must agree on the canonical form, and `he2tr` doubles as the display fallback wherever a card has no notebook `tr`.

⚠️ **There is a THIRD folding function, and it is deliberately not `trKey`: `cleRecherche` (same module) folds for SEARCH.** Searching and answering are different jobs, so they fold differently — `trKey` arbitrates an *answer*, where accepting a wrong one is serious, so it stays strict; `cleRecherche` arbitrates a *result*, where one extra word costs nothing and a missing one is a lie ("no results" reads as "the word isn't there"). It therefore drops the matres lectionis ו/י — `data/` stores vocalised *ktiv haser* (`מְסֻבָּךְ` → `מסבך`) while everyone types *ktiv male* (`מסובך`) — folds finals to their base letter, and applies the Latin folds **word by word** (trKey's `^` shva anchor would otherwise only see the first word of a haystack). Never route search through `trKey`, and never make the two one function.

⚠️ **A search fold has TWO ways to lie, and the second one passes every positive test.** Too strict and it hides a word that is present; too generous and an absurd query returns real words. Both were paid for once: `trKey`'s greedy gemination collapse (`(.)\1+`) reduced `qqqqq` to `k` and returned **449 cards** — `cleRecherche` therefore collapses **pairs only, consonants only** (measured: `he2tr` never emits a doubled consonant; the collapse exists solely to accept the geminated spelling one *types*, `shabbat` ≡ `shabat`). The rule that follows: **a search guard without a negative control proves nothing** — `verifieRecherche()` in `build.js` carries both halves, and both were seen failing.

⚠️ **The initial-shva rule is morphological, so `he2tr` only approximates it — and that is deliberate, not a pending bug** (measured over the whole corpus). Whether the shva is heard depends on the word's morphology, not its phonetics: the corpus keeps the `e` after the participle prefix מְ (272 words, no exception), after לְ/בְּ/וְ/נְ/רְ/יְ, and drops it inside a root cluster. `he2tr` therefore drops the `e` **after ש/ס/כ/צ only, and not before a guttural** (א ה ח ע ר) — the rule that maximised corpus agreement (each alternative was measured; adding ג cost 9 words and was rejected, which is why `gdolim` still comes out `gedolim`). **Do not "fix" the remaining misses by adding consonants to that class without re-measuring** — the harness is `node tools/mesure_translitteration.js`, which compares `he2tr(he)` to every hand-written `.tr` (exact rate, folded rate, total edit distance); run it before touching the rule, and reject any change that does not strictly improve all three. What protects the user meanwhile is `trKey`, which folds the optional initial `e` (`gdolim` ≡ `gedolim`): typing accepts both spellings whatever `he2tr` displays.

⚠️ **The harness is not a formality, and the "strictly improve all three" bar is not the whole test — a rising average hides individual losses.** Two rules were added this way (kamats katan of כל, and `ayv`→`av`): baseline exact 3557 / folded 3902 / distance 901 over 4229 pairs, after 3615 / 3970 / 830. But the *average* improving is not proof, so the real check is **pair-by-pair, old `he2tr` against new, both evaluated side by side in `vm` sandboxes** (`git show HEAD:src/app/js/02-translitteration.js` for the old one): count how many pairs move from accepted to rejected, and **demand zero**. That check is what caught the kamats rule over-firing on `כַּלְכָּלִי` when the harness average was already green — one real regression hidden among five *apparent* ones that were in fact faulty hand-written `.tr` (`kal` for כָּל, `bastayv` for בַּסְּתָיו, since corrected in `data/`). Corollary: **an improvement to `he2tr` doubles as an audit of the corpus** — the pairs it newly disagrees with are where the hand-written value is wrong, and `.tr` being authoritative means the tool never overwrites it, not that it is always right.

## The ritual after any change

⚠️ **Once per machine, before anything else: `git config core.hooksPath .githooks`.** The versioned `pre-commit` hook is what mechanically catches a stale artefact (including one committed without its `sw.js` stamp — `--check` recalculates the hash) or a blocking example error. Git does **not** enable it on clone — until you run that command the repo has *no* tripwire at commit time, and nothing says so. Check with `git config core.hooksPath` (must print `.githooks`). Assumed bypass, to justify in the commit message: `git commit --no-verify`.

1. `node tools/build.js` — reads `data/*.json` + `src/`, regenerates the **five** artefacts (notebook, `cards.json`, `app.html`, standalone, portal) and stamps `VERSION` in `sw.js`; fails if a section or an `EXPECTED_LEVELS` level drops to 0, if any entry lacks a valid `niveau`, or if a table entry lacks `theme` / carries a slug outside `EXPECTED_THEMES`. Check the printed counts.
2. If examples or vocabulary changed: `node tools/verifie_exemples.js` — **0 errors required** (warnings are editorial signals; `--strict` blocks on them too).
3. Verify the behaviour, **at the cheapest level that actually proves it**. `tools/build.js --check` already proves the five artefacts are all in phase with `data/*.json` + `src/` *and* that `sw.js` carries the matching stamp, so a content-only change is proven by steps 1–2 alone. Add a local server or jsdom when logic changed. **Reach for WebKit/Playwright only when you touched the UI** — markup, CSS, or a render path. Booting a real browser to re-confirm what `--check` just proved is comfort, not evidence, and it costs a tooling install plus a session of driving.
4. Nothing to do for `sw.js` — step 1 already stamped `VERSION` from the content it just wrote (trap 10). Just **commit `sw.js` with the artefacts**: split across two commits, the cache name lags a commit behind the content it names.
5. **The graph is never refreshed as part of the ritual — at most it gets FLAGGED (owner's rule).** `/graphify . --update` costs **~235k tokens** (measured); running it is always a separate, explicit decision. **The flag never triggers the update, and neither does anything else in this ritual.**
   - **A file was created, deleted or renamed** → add (or extend) the flag line in docs/TODO.md « Reprendre ici » : `⚠️ GRAPHE À RECALER : <fichiers>`. The flag records the debt so the next decided refresh knows why it runs — that is ALL it does.
   - **Any other change** — content lots in the notebook, `.md` prose, and even structural edits *inside* existing files: no refresh, no flag. That in-file drift is tolerated by design: `graphify explain` re-derives line numbers mechanically, and a graph/file disagreement is settled for the file. Say in the commit message that the graph was left as-is.
   - When a refresh IS explicitly decided (pending flag + a session that needs the map right), clear the flag in the same commit as `graphify-out/graph.json`.

   ⚠️ Bought once: refreshing after a pure-content lot cost ~4× the useful work and churned the graph (168 nodes added, 87 removed) rather than extending it — never run `--update` without a decision.
6. Update the docs (README, ARCHITECTURE, DESIGN, PRODUCT, TODO — especially « Reprendre ici »).
7. Commit per change, messages in French, then push to `main`. **This is a standing authorization from the owner, not merely a description of the procedure: pushing is the normal close of every change and is never to be asked for.** Announce it, don't request it. ⚠️ Stated explicitly because the temptation to ask is real and legitimate-looking — a push to `main` redeploys GitHub Pages, so it is outward-facing and would normally warrant a check-in. Here it does not. The rule is safe precisely because the tripwires stand upstream of it: the `pre-commit` hook runs `--check` and `verifie_exemples.js`, so what reaches `main` has already been proven in phase; and nothing is ever lost, since `git revert` restores artefacts and sources together (a plain revert leaves `--check` green — verify rather than assume).

Full version, with the tooling traps, in **docs/RITUEL.md** § Rituel à chaque modification — that file holds what does not change from session to session; `docs/TODO.md` holds what does.
